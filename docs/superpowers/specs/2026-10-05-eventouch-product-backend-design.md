# EVENTOUCH 통합 웹·PostgreSQL 아키텍처

> 개정: 2026-10-07. 이 문서는 2026-10-05의 파일 저장소/구형 ETKO 모델 사양을 대체한다.
> 목표: 운영사, 행사 매니저, 현장 스태프, 앱 설치 없이 링크로 접속하는 참가자가 하나의 서버와 행사 데이터에서 각자 필요한 웹 경험을 안전하게 이용한다.

## 승인된 결정과 경계

- 사용자는 통합형 단일 웹/API 서비스와 PostgreSQL 운영 저장소를 선택했다.
- Node PostgreSQL 클라이언트가 내장되어 있지 않으므로 `pg`를 유일한 새 런타임 의존성으로 추가하고 `package.json`/lockfile을 둔다. 기존 “내장 모듈만” 제약은 이 승인으로 변경한다.
- 동시성 검증은 운영 데이터와 분리한 일회성 로컬 PostgreSQL Docker 컨테이너만 사용한다. 실제 서비스 배포, 운영 DB 접속, NAS 마운트는 하지 않는다.
- UI와 데이터 계약의 기준은 현재 `assets/js`의 EVENTOUCH 버전 9 모델과 기존 경로·브랜드다. 구형 `server/api.js`의 ETKO v1 계약은 운영 계약이 아니다.
- SMS OTP, 참가자 계정, 실제 이메일/알림톡/SMS 발송, 실제 결제·환불 연동은 별도 승인 전까지 만들지 않는다. 참가자는 행사 링크와 개인 티켓 링크로 접근하며 앱 설치나 회원 가입이 필요 없다.
- 참가자 CSV 가져오기는 유지한다. 기존 브라우저 데모 자료를 운영 DB로 자동 이관하지 않는다.
- 산출물은 코드·설정·문서까지만이다. 실제 배포/게시/외부 전달은 별도 승인 대상이다.

## 시스템 형태

- 정적 프런트엔드와 Node HTTP API는 같은 제품 저장소와 단일 배포 단위에 둔다. PC용 운영 콘솔, 모바일 우선 스태프 업무 화면, 모바일 참가자 화면은 역할과 업무에 맞게 다르게 제공한다.
- 운영 데이터의 유일한 기준은 PostgreSQL이다. 브라우저 `localStorage`는 정식 저장소나 인증 수단으로 쓰지 않는다. 허용된 오프라인 체크인 대기열만 클라이언트에 남기고 재연결 시 서버가 중복을 판정한다.
- PostgreSQL은 `pg` Pool로 접근한다. 계정·세션·행사·행사 멤버십·초대·멱등성 키는 관계형 제약으로 보호하고, 버전 9의 행사별 workspace 데이터는 JSONB로 보존한다. 각 쓰기 명령은 한 DB 트랜잭션에서 행사/workspace 행을 잠가 정원·중복 신청·체크인 경쟁 조건을 직렬화한다.
- DB 스키마 변경은 번호가 붙은 SQL migration으로 관리한다. 운영 환경은 `DATABASE_URL`을 필수로 하고, 비밀값은 환경변수에서만 읽는다.
- 업로드 파일은 PostgreSQL blob이 아니라 `STORAGE_DIR/eventouch/{photos,reports,exports}` 아래에 보관하고 DB에는 메타데이터만 둔다. 경로·크기·콘텐츠 유형을 서버에서 검증한다.

## 계정, 참가자, 권한

- 운영 계정은 버전 9 역할 `AGENCY`, `MANAGER`, `STAFF`와 현재 행사 멤버십/업무 배정을 따른다. 구형 `CLIENT`, `VIEWER`, `DESK`, `BOOTH` 계정 역할을 되살리지 않는다. 고객 담당자 연락처는 현재 제품 정책대로 내부 기록으로만 유지한다.
- 운영자 비밀번호는 scrypt 해시로 저장한다. 초대 수락 시 사용자가 비밀번호를 설정한다. 시드 운영자는 환경 변수로만 구성한다. 초대 전달은 당분간 수동 링크이며 이메일 발송은 하지 않는다.
- 세션은 난수 bearer 값을 HttpOnly/SameSite 쿠키로 전달하고 DB에는 해시만 보관한다. 세션 만료·로그아웃·권한 변경은 서버에서 적용한다.
- `AGENCY`는 운영사 범위, `MANAGER`는 멤버십이 허용된 행사 범위, `STAFF`는 활성 업무 배정(데스크/부스)의 범위와 동작만 서버가 매 요청 확인한다. 화면에서 메뉴를 숨기는 것은 서버 권한 검사를 대체하지 않는다.
- 참가자 공개 API는 공개된 행사 안내와 요청 티켓이 가리키는 본인 자료만 반환한다. 참가자 본인 확인에 OTP를 추가하지 않는다(미승인 결정). 티켓 링크는 추측하기 어려운 bearer credential로 취급한다.

## API와 데이터 흐름

- 로그인/로그아웃/세션 확인, 역할별 bootstrap 조회, 공개 행사/티켓 조회, 참가자 신청, 운영 명령, 체크인, 파일 업로드·다운로드 API를 제공한다.
- 프런트엔드는 기존 `E.run(command, payload)` 행위를 같은 command ID로 서버에 보내고 서버의 권한·업무 규칙 검증 및 트랜잭션 결과를 적용한다. 중복 command ID는 재실행하지 않는다. 브라우저가 보내는 역할/권한/수정된 전체 상태를 신뢰하지 않는다.
- 공개 참가자 신청은 별도 계정 없이 행사별 등록 상태·동의 문구·중복·정원 규칙을 서버에서 확인한다. 발급 티켓만 본인 티켓 페이지와 참여 동작의 범위 증명으로 사용한다.
- 오프라인 체크인 재생은 명시적인 command ID를 유지하고, DB 멱등성 제약으로 재전송에 안전하게 만든다.
- 메시지 발송은 계속 `SIMULATION_ONLY`/미연동 상태다. 예약 기록과 실제 외부 발송을 혼동하지 않게 한다.

## 수용 기준

- 독립 DB를 대상으로 migration, 재시작 후 지속성, 계정/세션, 관리자·매니저·스태프 접근 매트릭스, 공개 티켓 경계, 신청 정원 경쟁, 중복 체크인 및 재전송을 검증한다.
- 핵심 흐름: 운영자 로그인 → 행사 준비 → 스태프 배정 → 앱 없는 참가자 신청/티켓 조회 → 스태프 체크인 → 운영 현황 재조회.
- 두 브라우저/세션에서 같은 PostgreSQL 데이터가 보이고, 새로고침/서버 재시작 뒤에도 저장 결과가 남는다.
- 실제 제품 UI를 지원 브라우저에서 1280px 및 390px로 검증한다. 신청·체크인 흐름, 권한 거부, 키보드 포커스와 콘솔/네트워크 오류를 확인한다. 렌더 리뷰가 필요한 시각 변경은 OpenDesign이 수행한다.
- 테스트와 로그에 실제 참가자 개인정보·비밀값을 넣지 않는다. 비밀번호 원문·세션 원문·티켓 원문을 로그/저장소에 남기지 않는다.

## 제외

- SMS OTP, 실제 알림톡/SMS/이메일 공급자, 결제 게이트웨이와 실환불, 소셜 로그인.
- 실제 클라우드 배포, 도메인/인증서 설정, NAS 실마운트, 기존 브라우저 저장 데이터의 일괄 자동 이전.
- 네이티브 참가자 앱이나 역할별 별도 서버/마이크로서비스.
