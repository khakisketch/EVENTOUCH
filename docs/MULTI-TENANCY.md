# 조직 격리(멀티테넌시) 설계

Status: 설계안 + 1단계(additive 스키마 `008_organizations.sql`) 적용됨. 기존 동작 불변. 매핑·스코프·롤아웃은 별도 승인 후.
Related: `docs/ARCHITECTURE.md` 1절 목표, `docs/STATUS.md` 블로커.

## 현재 상태 (단일 조직 전제)

- `001_initial.sql`에 조직 테이블·테넌트 컬럼이 없다.
- `AGENCY`는 전역 우회(`server/access.js`), 전체 행사·계정·고객사·초대 조회(`server/state.js`).
- `org_permissions`·`memberships.write_permissions`는 저장되지만 쓰기 판정은 역할·소속 중심이다.
- 결론: 대행사 계정을 추가해도 격리된 조직이 생기지 않는다. 여러 회사에 제공할 수 없다.

## 설계 기준

1. **전역 계정과 조직 소속을 분리**한다. 계정은 로그인 식별자, 권한은 조직별 멤버십이 가진다.
2. **조직 컨텍스트는 인증된 멤버십에서만 유도**한다. 요청의 `orgId`를 신뢰하지 않는다.
3. **소유 범위**: `clients`·`events`(경유 자식 전부)·`invitations`·`staff_assignments`·`memberships`·파일·`command_receipts`·`message_outbox`·발송 설정. 자식은 소속 행사 경유로만 해석한다.
4. **공개 주소**: `events.slug`는 당분간 전역 유일 유지. `/event/:slug`가 모호해지지 않는다.
5. **멱등성 보존**: `command_receipts` 조회·재전송 범위를 조직·행사·주체로 좁히되, 키 충돌 의미를 바꾸지 않는다.

## 미결정 (구현 전 확정)

- 계정의 복수 조직 소속 허용 여부와 조직 전환 UI 유무.
- PostgreSQL RLS 사용 여부(정책 vs 애플리케이션 스코프).
- 기존 데이터의 조직 소속 매핑(단일 조직 승격 vs 수동 지정).
- PII·인증 챌린지·감사 로그 보존 기간과 암호화·백업 정책.

## 이행 순서 (승인 후)

1. 조직·조직 멤버십 스키마 추가(additive only), 기존 동작 불변.
2. 기존 데이터 매핑 감사(건수·관계·입장 토큰·체크인 이력 보존 확인).
3. 읽기·쓰기 이중 경로(스코프 적용 + 구 경로) → 2테넌트 음성 행렬 검증.
4. 제약·기본값 고정 → 재시작 유지·백업 복구 리허설 → 배포 승인.

## 검증 행렬 (롤아웃 게이트)

- 테넌트 A/B 읽기·쓰기·초대·재설정·파일·엑스포트·영수증·백그라운드 작업 교차 차단.
- 기존 데이터 마이그레이션 전후 ID·건수·관계·토큰·이력 동일.
- 관련 PostgreSQL 테스트는 직렬·격리 DB, 웹 빌드·타입·브라우저 흐름 통과.

## 이번 변경에서 하지 않은 것

- 마이그레이션·RLS·조직 전환 UI·공유 호스팅. 이 문서는 설계 경계 확정이 목적이다.
