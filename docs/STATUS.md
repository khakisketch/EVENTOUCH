## 제품

행사대행 운영사를 위한 웹 제품 하나. **제품 UI 기준은 `apps/web`(Next.js + TypeScript) 하나**다.
운영 콘솔·현장 스태프·참가자·전광판은 같은 출처의 `/api/*`로 공용 Node API와 PostgreSQL을
사용한다. 2026-10-17 사용자 승인에 따라 구 바닐라 프론트엔드·정적 진입점·로드 순서와
구 UI 전용 테스트를 제거하고 기본 실행·배포·검증·문서 기준을 Next로 통일했다.
공용 API·인증·DB·업로드·과도기 저장소와 사용자 데이터는 폐기 대상이 아니다.

독립 평가 후 종합. 정량 usability 수치(발견율·소요시간)는 만들지 않았고 실사용자 관찰이 없다는 한계가 있다.

- **화면별**: 명확 5(행사·고객사·운영현황·현장사진·경품) / 보통 10 / 부담 1(추첨·투표). 추첨·투표는 투표·무대
  추첨·룰렛·럭키번호 설정이 한 화면에 이어져 1280px에서도 3168px 길이가 났다(상단 섹션 점프는 있음).
- **확정해 고친 것(3건)**: ① 경품 `수령 처리`에 확인이 없었는데 서버는 수령 후 취소를 거부한다 →
  되돌릴 수 없다는 확인 추가. ② 참가자 화면 `전체 N명`은 취소 포함인데 운영현황·보고서는 `취소 제외` 기준이라
  14 vs 13처럼 어긋나 보임 → `취소 포함` 명시. ③ 검색 접근 이름이 `참가자 이름 검색`인데 실제는
  이름·소속·연락처 검색 → 실제 기능과 일치.
- **오진으로 확인한 것**: 44px 미만 조작 목표는 16개 화면 1280·390 전수 실측에서 **0건**(20px 네이티브 체크박스는
  44px 이상 라벨 안에 있어 실eff 타깃이 통과). 로딩 패널의 `onRetry`는 빈 함수가 아니라 실제 재조회다.
- **남은 판단 필요**: 비가역 명령의 확인 문법 혼재(네이티브 confirm ↔ 인라인 2단계), 추첨·투표 화면의 영역 분리,
  모바일 참가자 행의 반복 조작(행당 체크·상태·작업 3단), 명단 가져오기 첫 화면에 단계 표시 없음.
  참가자 수 기준·그룹 지정 범위·경품 지급 확인은 앞선 회차와 이번 회차에 이미 반영했다.

평가에서 나온 4개 항목을 개발로 반영했다.

1. **확인 문법 통일**: 되돌릴 수 없거나 외부로 나가는 명령은 공용 `ConsoleConfirm`(role="group"·"실행 확인",
   요약 → 확인/취소, 확인 버튼으로 포커스 이동)으로 화면 안에서 확인한다. 네이티브 `window.confirm`은 12개
   화면(메시지·경품·참가자·추첨·프로그램·콘텐츠·현장운영·사진·참가자페이지·팀·고객사)에서 사라졌고, **대화상자
   닫기 게이트**(작성 중 내용 버리기·응답 미확인)는 ConsoleDialog·canClose 계약이므로 그대로 남겼다.
   모든 요약 문구는 기존 네이티브 confirm 문구를 그대로 옮겼다.
2. **추첨·투표**: 행사 중 하는 일인 `무대 추첨`을 첫 섹션으로 올리고, 사전 설정(추첨 프로그램·룰렛 운영·
   럭키번호 범위·투표 팀 등록) 폼은 접이식으로 접었다. 접힌 요약은 **현재 값**을 보여 줘서
   (`추첨 프로그램 설정 · 2개`) 닫혀 있어도 무엇이 설정돼 있는지 보인다. 페이지 길이 3168→1743px.
3. **모바일 참가자 행**: 승인 원탭은 그대로 두고, 경품 등록·상태 변경은 `더보기` 토글로 접었다(기본 접힘). 이름과 상태를 한 줄에 두고(한 눈에 명단 읽기), 행 동작은 오른쪽 아래에 두었다. `더보기`는 스크린리더에서 `이름 참가자 작업 열기`로 읽힌다.
4. **명단 가져오기**: 가져오기는 **선택적 도구**라 첫 화면에 그렇게 밝히고(공개 신청이 기본 경로), 3단계 표시는
   **파일을 고른 뒤에만** 나타난다. 필수 절차처럼 보이지 않게 했다.

검증은 `tests/console-confirm-grammar.test.cjs`·`tests/console-operator-evaluation.test.cjs`와 콘솔 감사
(71판정)·`npm test` 708·접근성·모바일·실제 렌더로 확인했다. 계측 원본은
`/tmp/opencode/eventouch-captures/console-ux-evaluation/`의 `measurement.json`·`controls.json`·
`touch-targets.json`·`renders/`에 있다.

### 전 화면 사용성·설계 점검(16메뉴 + 참가자 + 스태프, 최신 빌드 렌더 기준)

16개 콘솔 메뉴(1280·390)·참가자 모바일·스태프 현장·조직 영역을 **최신 빌드 렌더를 직접 읽어** 화면별로
점검했다(독립 검토 3팀 + 자가 점검). 판단 기준은 작업 비용·정보 위계·피드백·오류/빈 상태·터치·키보드·용어
일관·`docs/DESIGN-SYSTEM.md` 규약 적합이다. 확인된 개선 후보와 함께 **결함이 아닌 것으로 판정한 것**도
함께 기록한다.

**고치기로 한 것**
- 메시지: 수신자 선택이 긴 폼 아래쪽에 있어 "누구에게 보내는지"를 놓칠 수 있었음 → 작성 흐름에서 수신자
  상태가 보이고 한 번에 이동하도록 배치 정리.
- 추첨·투표: 전제 미충족 시 실행 버튼이 읽히지 않을 정도로 흐렸고, 미충족 이유가 버튼에서 떨어져 있었음 →
  비활성 상태의 가독성 + 버튼 옆 전제/다음 행동 연결.
- 참여 프로그램: 카드가 늘면 찾기 비용이 커지고 목록을 줄이는 수단이 없었음 → 이름 검색·진행 상태 필터와
  결과 수 안내.
- 행사 설정(모바일): 점프 내비는 있으나 현재 위치 표시가 없어 긴 화면에서 자신이 어디 있는지 몰랐음 →
  현장 운영·추첨·참가자 페이지 편집기와 같은 "현재 위치" 패턴 적용.
- 스태프 부스 인증: 성공 뒤 입력창·버튼이 남아 다음 행동이 불분명했고, 긴 `ET:BOOTH:` 코드가 잘려 확인이
  어려웠음 → 성공 후 입력 비움·다음 참가자 동작 명시·코드 복사 경로.

반영 후 `npm test` **762 통과**, 콘솔 감사 **73판정**, **과제 기반 사용성 9/9**(조작 1~6회·키보드 최단
2~34회), 접근성 위반 0, 모바일 72검사를 다시 통과했다. 새 계약 3건
(`tests/console-messages-recipient-flow.test.cjs`·`tests/console-draws-programs-usability.test.cjs`·
`tests/console-settings-staff-usability.test.cjs`)이 각 개선을 고정한다.

**결함이 아니었다고 판정한 것(오조작 방지)**
- 운영 현황 "확정자 중 미입장" 상자: 이미 참가자 목록(`status=APPROVED&attendance=NOT_ENTERED`)으로 가는 링크.
- 콘텐츠 공지 "삭제": 위험 작업인데 일반 작업과 같은 비중 → 그러나 삭제 전 확인 대화상자 절차가 이미 있다.
- 참가자 홈 6타일: 고객사 결정(초기 심플 구성)대로 유지.

### 배포본 최신화 + 배포 검증(실사용 시나리오)

배포 이미지(`eventouch-web`, `eventouch-eventouch`)가 **10-17 빌드**로 4일 물러나 있어 이번 작업이 전혀
반영돼 있지 않았다(참가자 추가 버튼조차 없었다). `docker compose up -d --build`로 정본 경로에서 갱신했다.
**기존 볼륨(`eventouch_eventouch-pgdata`·`etko-db`·`etko-storage`)과 DB 비밀번호는 그대로** 사용해 데이터
리셋은 없었다.

새로 **관리자(조직 소유자) 계정**을 만들어 배포본에서 실제 시나리오를 한 바퀴 돌았다:
행사 생성 → 참가자 등록 → 데스크 생성 → 부스 생성 → 현장 스태프 초대 → 수락(계정 생성) → 데스크 배정 →
**스태프 계정으로 로그인해 현장 화면에서 배정된 데스크 확인**까지 통과했다.

- **부스 인증 기능 선행조건을 어디서 켜는지 알려주지 않았다**: 현장 운영 화면은 "부스 인증 기능을 먼저 켜야
  합니다"만 말해 두 화면을 오가게 했다. → **"행사 설정의 기능에서 켜면…"** 안내와 **"부스 인증 기능 켜기"**
  링크(행사 설정 · 기능 앵커로 이동)를 추가했다.
- **배포 검증 최소 기준(헬스 → 로그인 → 콘솔 → 쓰기 1건 → 파일 1건 → 재시작 후 유지) 통과**: `/api/health`
  200, 새 관리자 로그인, 콘솔 진입, 공지 1건(201), PNG 파일 1건(201), 컨테이너 재시작 후 공지·파일(200, 70바이트
  PNG)·계정·행사 모두 유지. 검증용으로 만든 중복 행사 4개는 지우고, 예시 행사 1개(참가자·데스크·부스·배정 각
  1건)는 직접 살펴볼 수 있게 남겼다.

### 과제 기반 사용성 검사(새 도구) — 목표당 조작 수로 재는 사용성

화면이 "잘 만들졌다"를 재는 도구가 없었다(소스 계약은 문자열 검사, axe는 구조만 본다). 그래서 **실제
목표를 주고 몇 번의 조작으로 끝나며 어디서 막히는지**를 재는 검사(`npm run audit:usability`)를
만들었다. 9개 과제(운영자 5·참가자 4)를 실제 격리 API/DB에서 조작하며 조작 수·스크롤 수·주요 버튼까지의
키보드 Tab 수·서버 상태 반영·오류를 함께 잰다.

첫 회차에서 **검사 도구만으로는 안 잡혔던 실제 결함 2건**이 나왔다.

- **키보드 도달성**: 콘솔 사이드바에 메뉴 16개가 있어 주 버튼까지 Tab이 수십 회 필요했다(수신자 목록을
  펼친 메시지 화면은 47회). → 콘솔에 **"본문으로 건너뛰기"** 스킵 링크를 넣고, 포커스를 본문으로 옮겼다.
- **스태프 배정 자체가 불가능**: 서버의 계정 조회가 "멤버십 또는 배정이 있는 계정"만 담았다. 그런데
  초대 수락 시 STAFF 계정에는 멤버십이 생기지 않고(초대 안내도 "수락 후 데스크·부스 배정으로 연결한다"고
  말한다), **배정해야 계정이 보이는** 순환이 생겨 신규 스태프를 현장에 붙일 방법이 없었다. → MANAGER의
  계정 조회에 **아직 어느 행사에도 배정되지 않은 STAFF 계정**을 포함했다. 안내 문구도 "계정을 만든 뒤 다시
  시도하세요"에서 실제 다음 단계(팀·권한에서 현장 스태프 초대)를 말하도록 바꿨다.

- **참가자 쪽 스킵 링크가 포커스를 옮기지 못했다**: 루트 레이아웃의 스킵 링크가 일반 앵커라 뷰포트만
  움직이고 포커스는 그대로였고, 참가자 `<main id="main-content">`에는 포커스 수용 수단이 없었다. →
  **공용 `apps/web/app/SkipLink.tsx`** 하나로 통일해(포커스 이동 + 필요 시 `tabindex="-1"` 부여) 콘솔과
  참가자 전 화면에 적용하고, 참가자 21곳 본문 영역에 `tabIndex={-1}`을 넣었다. 실제로 Tab 1회 → 링크가
  보임 → Enter → `main-content`가 포커스를 받는 것을 **양쪽(참가자 공개 페이지·운영 콘솔) 직접 조작으로
  확인**했다. 계약 `tests/skip-link.test.cjs`가 규칙을 고정한다.

**최종 측정(9개 과제 전부 통과)**: 조작 수 1~6회(상한 10~12), 스크롤 0~4회, 키보드 최단 경로 2~34회.
스킵 링크를 쓰지 않고 맨 위에서만 Tab을 눌렀을 때의 값(26회 등)도 함께 남긴다. 검사는 제품·기존 스크립트를
고치지 않고 새 파일 1개와 npm script 1줄만 추가했다. 수치는
`/tmp/opencode/eventouch-captures/usability-<날짜>/result.json`에 남는다. 이 도구는 **이해도·선호·실기기·
스크린리더 낭독**을 재지 못한다.

### 사용성(UI/UX) 전면 개선 — 기능 추가 없이 조작 비용·표현·피드백 정리

"기능이 아니라 사용성"이라는 지시에 따라, 화면을 다시 보며 **작업 비용·정보 위계·피드백·오류 안내**를
정리했다. 남은 지적을 실측해서 고친 뒤 전 검증을 다시 돌렸다.

- **긴 콘솔 화면 3곳에 같은 "현재 위치" 패턴**: 현장 운영·추첨·투표·참가자 페이지 편집기는 한 화면에
  여러 종류의 작업이 이어져 있어, 지금 무엇을 보고 있는지 바로 알 수 없었다. 세 화면 모두 점프 내비 옆에
  **"현재 위치: …"** 를 두고 화면에 보이는 구역을 따라가게 했다(기존 앵커·점프는 그대로, 관찰은 추가).
  참가자 페이지 편집기는 미리보기가 맨 아래라 대조 비용이 컸는데, 같은 내비로 바로 갈 수 있다.
- **모바일 참가자 명단 행 밀도**: 14명만 스크롤이 오래 걸리고 상태 칩이 한 줄을 따로 쓰고 있었다. 이름을
  **상태 칩과 같은 줄**에 두고(한 눈에 명단 읽기), 행 동작은 오른쪽 아래로 모았다. `행 동작`이라는 모호한
  라벨은 **"더보기"**로 바꾸고, 스크린리더에서는 `이름 참가자 작업 열기`로 읽히게 했다.
- **참가자 "티켓 없음" 안내 3면 통일**: 홈의 기능 탭·티켓 화면·참여 프로그램 화면이 같은 상황을 서로 다른
  말과 다른 버튼 이름으로 알려 주고 있었다. 셋 다 **"티켓이 확인되지 않습니다" + "내 티켓 찾기"**로
  맞췄고(설명 문장·신청 경로는 유지), 복구 화면의 **"행사 안내 확인"** 은 **"행사 안내·문의처 보기"**로
  바꿔 무엇을 확인하러 가는지 분명히 했다(행사 안내에 문의처가 있다).
- **부스 인증 한도 초과**: 이유만 있고 대안이 없었다 → **"다른 열린 부스 N곳에서 인증할 수 있습니다"**
  (열린 부스가 없으면 현장 운영자 문의)로 서버가 다음 행동을 함께 말한다.
- **대량 승인 결과**: "N명 승인"만으로는 목록과 대조가 안 됐다 → **승인한 사람 이름**(3명 초과 시 "외 N명")
  을 결과 문구에 넣는다.
- **스태프 최근 처리 목록**: 데스크 기록과 부스 기록이 섞여 "지금 한 일"을 찾기 어려웠다 → **현재 업무
  기준**으로 거르고 머리말에 범위를 적는다("최근 처리 · 데스크 체크인" / "· 부스 인증").

검증은 `npm test`, 콘솔 감사 73판정, 접근성 0, 모바일 72검사, 웹 감사 0과 스태프·참가자 실제 조작으로

### 최종 재검토 반영(독립 검토 5건 중 실행 가능한 4건)

전체 제품(콘솔 16메뉴 + 참가자 웹 + 스태프 현장)을 최신 빌드 기준으로 독립 재검토하고, 나온 지적을
실제로 고친 뒤 다시 검증했다.

- **스태프 최근 처리 목록을 업무별로 분리**: 데스크 작업 화면에 부스 인증 기록이, 부스 작업 화면에 데스크
  입·퇴장 기록이 섞여 "지금 한 일"을 확인하기 어려웠다. 목록을 **현재 업무 기준으로** 거르고 머리말에
  범위를 적는다("최근 처리 · 데스크 체크인" / "최근 처리 · 부스 인증").
- **부스 인증 한도 초과에 다음 행동 안내**: 한도를 다 쓴 참가자에게는 이유만 있고 대안이 없었다. 서버는
  그 시점에 행사의 다른 부스를 알고 있으므로 **"다른 열린 부스 N곳에서 인증할 수 있습니다"**를 함께
  말한다(열린 부스가 없으면 현장 운영자에게 문의하도록 안내).
- **대량 승인 결과에 이름**: "N명을 승인했습니다"만으로는 목록과 대조가 안 됐다. 승인한 사람의 이름(3명
  초과 시 "외 N명")을 결과 문구에 넣는다.
- **참가자 "티켓 없음" 표현 통일**: 홈의 기능 탭·티켓 화면·참여 프로그램 화면이 같은 상황을 서로 다른
  말과 다른 버튼 이름("내 티켓 찾기" / "내 참가 정보 다시 연결" / "내 티켓으로 이동")으로 알려 주고 있었다.
  셋 다 **"티켓이 확인되지 않습니다" + "내 티켓 찾기"**로 맞췄고, 설명 문장과 신청 경로는 그대로 남겼다.
- **참가자 홈 구조는 그대로**: 고객사 결정(초기 6타일 심플 구성)을 그대로 지킨다. 티켓이 없는 참가자가
  6개 타일에서 막히지 않는지 실제로 눌러 확인했다(6개 모두 신청·복구로 이어짐, 페이지 오류 0).

### 참가자 홈: 고객사 결정 반영(초기 심플 구성 유지)

참가자 홈 구조는 안과 상태를 거쳐 **고객사가 초기 심플 구성을 그대로 쓰기로 결정**했다. 근거는
**"QR이 참가자들에게 제공되지 않을 수도 있다"**는 점이었다. 즉 홈이 QR 중심 구조를 가정하면 안 된다.

- **반영**: 홈 상단에 붙였던 **내 입장 티켓 QR 카드를 제거**해, 홈은 배너 + 6개 기능 타일로 되돌렸다
  (모바일 티켓·공지사항·럭키드로우 번호·룰렛 이벤트·순위 투표·부스 인증). qrcode 의존은 티켓 화면에만
  남는다.
- **티켓은 한 번의 탭으로 간다**: "모바일 티켓"이 첫 번째(필수) 타일이라 목록을 헤맬 필요가 없다. 티켓이
  없으면 그 화면이 "티켓이 확인되지 않습니다. 신청 후 이용하세요" + **참가 신청하기**로 이어진다.
  QR이 제공되지 않는 행사에서도 참가자 동선은 끝까지 이어진다.
- **판정·계약 갱신**: 웹 감사의 "입장 QR이 첫 화면에 보여야 한다" 판정은 이 결정과 정면으로 어긋나
  폐기하고, 같은 자리에 **6개 항목이 유지되고 티켓 진입이 첫 화면에 있으며 홈에 QR이 없다**는 판정으로
  바꿨다. 계약 `tests/attendee-home-entry-ticket.test.cjs`도 "심플 목록·티켓 한 번에 도달·신청 경로·
  티켓 토큰은 탭 메모리에만 존재"를 고정한다.
- **실측**: 티켓 보유/미보유 × 390×844·320×568 네 조합에서 6타일 유지·홈 QR 0·티켓 진입 첫 화면 노출·
  넘침 0을 확인했다(`/tmp/opencode/eventouch-captures/attendee-home-simple/`).

### QR 스캔 가능성 수정(참가자가 스태프 QR을 못 읽던 결함)

참가자 측 흐름을 반복 검수하면서 스태프가 보여주는 **부스 QR이 실제로 카메라로 읽히지 않는** 문제를
찾았다. 스캔 경로는 서버 계약·권한·멱등과 무관한 **화면 결함**이었다.

- **원인 1 — 조용한 여백(quiet zone) 없음**: `react-qr-code` v2는 QR 규격(ISO/IEC 18004)이 요구하는
  4모듈 여백을 그리지 않는다. 티켓·홈 QR은 카드 패딩이 우연히 여백을 대신해 읽혔지만, 스태프 부스 QR은
  여백이 전혀 없었다. 부스 페이로드는 행사 ID와 UUID 부스 ID를 함께 담겨 모듈 37개가 200px에 밀리고,
  규격이 요구하는 4모듈은 21.6px 필요하다. 참고로 같은 QR 마크업을 합성 페이지에 두면 해독되어,
  제품 렌더 경로의 문제임을 확인했다.
- **원인 2 — 빈 고정 도크가 QR을 덮음**: SELF 부스 모드에서는 스캔 폼과 카메라 버튼이 모두 없어
  스캔 도크가 비는데, 그 빈 도크가 모바일에서 `position: sticky`로 떠서 QR 하단 12px를 덮었다.
  고정이 해제되자 곧바로 해독되었다. 참가자가 스태프 화면을 찍으면 **스태프 자신의 빈 바가 QR을 가려**
  스캔이 실패하는 현장 차단 결함이었다.
- **수정**: 세 QR 표면(스태프 부스·참가자 티켓·참가자 홈)에 흰 여백 프레임(24px)을 넣고, SELF 부스
  모드에서는 빈 도크를 아예 띄우지 않으며, 부스를 고르면 QR이 화면 가운데로 오도록 스크롤한다.
- **계약**: 새 소스 계약 `tests/qr-scannability.test.cjs`가 여백 존재·여백이 4모듈을 충족하는 계산·
  빈 도크가 QR을 덮지 않는 것·QR이 화면에 들어오는 동작을 고정한다.

### 참가자 티켓·복구 흐름 단순화

신청 흐름에 이어 참가자가 실제로 쓰는 두 화면(티켓·티켓 찾기)도 같은 기준으로 손봤다.

- **티켓 화면**: QR이 주역이 되도록 `참여 프로그램 보기`를 보조 버튼으로 낮췄다(같은 카드에서 주황 버튼이
  두 개이면 QR이 눈에 띄지 않는다). 안내는 "입장할 때 이 QR을 보여 주세요. 퇴장할 때도 같은 QR을
  사용합니다"처럼 할 일로 바꿨고, "현재 탭에만 보관" 설명은 조용한 각주로 내렸다. 티켓이 없거나 실패한
  상태는 복구·재신청·행사 안내로 항상 이어진다.
- **티켓 찾기(복구)**: 한 번에 한 단계씩 보여 주도록 `1. 연락처 확인 → 2. 인증번호 입력`을 넣고,
  10분 유효·문자 도착 확인 불가·재발송/연락처 변경 경로를 각각 분리했다.

검증은 `tests/attendee-ticket-flow.test.cjs`와 실제 렌더(390px)로 확인했다. 근거 렌더는
`/tmp/opencode/eventouch-captures/attendee-register-review/ticket-390.png`·`recover-390.png`.

### 참가자 신청(등록) 흐름 단순화

사용자가 "참가자가 등록할 때 모두 사용성이 단순하고 편하면 좋겠어"를 지시해, 참가자 측 신청 흐름을 손봤다.
참가자 홈 구조 결정(고객사 회신 대기)과 달리 신청 폼은 별개 표면이라 바로 진행했다.

- 신청 첫 줄에 **"신청 정보를 입력하면 참가 티켓이 바로 발급됩니다"** 안내를 넣었다(인증 필요 행사면
  "연락처 인증 후 …"). 결과가 즉시 보인다는 사실이 신청 부담을 낮춘다.
- **연락처 인증을 입력란보다 앞으로** 옮겼다. 인증은 신청의 전제인데, 전부 입력한 뒤에야 발견되던
  순서를 바꿨다.
- **중복 신청**은 거절만으로 끝내지 않고 `이미 신청하신 연락처로 등록되어 있습니다`와
  `내 티켓 찾기` 연결을 함께 보여 준다. 재신청은 흔하고 복구 가능해야 한다.
- 키보드 자동완성을 붙였다(이름·이메일·소속·연락처). 휴대폰에서 이름·소속을 다시 타이핑하지 않게 한다.

검증은 `tests/attendee-registration-flow.test.cjs`와 실제 렌더(390px)로 확인했다. 근거 렌더는
`/tmp/opencode/eventouch-captures/attendee-register-review/register-after-390.png`.

### 참가자 홈에 입장 QR 노출 + 대량 승인 + 메시지 수신자 목록 접기

참가자가 현장에서 티켓을 바로 제시하도록, 그리고 운영자가 대량으로 처리하도록 남은 항목들을 개발했다.

- **참가자 홈에 입장 QR 카드**: 홈 첫 화면(행사 이미지 뒤)에 내 티켓 카드(QR·이름·"입장할 때 이 QR을 보여
  주세요")를 넣었다. 6개 기능 타일 중에서 티켓을 찾지 않아도 된다. QR은 이 탭에 보관된 티켓이 있을
  때만 노출되고, 지참자 화면의 2열 타일 구성과 배너는 그대로 두었다. 웹 감사에 "티켓이 있으면 첫 화면에
  QR이 보인다"(320·390·1280)를 새 판정으로 추가했다.
- **대량 승인**: 서버는 이미 `participant.status`에 ids 배열(최대 1000명)을 받는데 화면이 쓰지 않았다.
  참가자 선택 줄에 `선택 승인`을 추가해 선택한 승인 대기자를 한 번에 확정한다(선택 안의 PENDING만 대상,
  지문별 command id 유지으로 응답 유실 시 같은 요청 재시도).
- **메시지 수신자 목록 접기**: 작성·수신자 선택·예약·발송이 한 화면에 이어지던 것을, 검색과 선택 요약은
  그대로 둔 채 **수신자 목록만 접도록** 했다. 승인 대기자가 섞인 경고는 접힌 안에 숨지 않고 요약 옆에 둔다.

검증은 `tests/attendee-home-entry-ticket.test.cjs`·`tests/console-participant-entries.test.cjs`와 콘솔 감사
신규 판정 `operator/bulk-approve`(여러 명 선택 → 일괄 승인 → 서버 상태 재조회), 웹 감사의 티켓 QR
첫 화면 판정, 실제 렌더로 확인했다. 근거 렌더는 `attendee-register-review/home-ticket-390.png`·
`attendee-register-review/ticket-390.png`와 콘솔 감사 `operator/bulk-approve.png`다.

### 참가자 관리 재구성(등록 경로 3가지)

사용자가 "명단 가져오기가 강제될 필요가 있나요"를 지적한 뒤, 명단 추가 입구가 사실상 파일 가져오기뿐이었다는
사실을 코드에서 확인했다(참가자 추가 버튼 없음, `participant.create`는 서버에 있으나 콘솔 화면 미노출). 등록
경로를 세 가지로 정리했다.

- **참가자 추가**(신규): 한 명을 직접 등록하는 대화상자. 이름·연락처(필수)·소속·이메일·등록 방식.
  `participant.create`를 일반 명령 경로로 보내고, 지문별 command id를 유지해 응답 유실 시 같은 요청으로
  재시도한다. 등록 방식은 `사전 등록`(이름이 이미 정해진 명단) / `현장 등록`(당일 추가)이며 서버가
  `registrationType`으로 기록한다(기존 기본값 `ONSITE` 유지, 공개 위조 금지).
- **파일로 등록**(기존 가져오기): 도구로 유지하되 명칭을 등록 경로에 맞게 바꿨다. 가져오기 화면은 선택적
  도구임을 첫 화면에 밝히고 3단계 표시는 파일을 고른 뒤에만 보여 준다.
- **참가 신청 링크 복사**(신규): 참가자가 스스로 신청하는 경로. 빈 화면에 "참가자를 직접 추가하거나 파일로
  등록할 수 있습니다"와 "참가자가 스스로 신청하게 하려면 행사 설정의 참가 접수를 열어 주세요"를 함께 보여 준다.
- 목록 화면의 `참가자 추가`는 **참가자 목록 섹션 머리**에 두었다. 도구막대에 넣으면 모바일에서 버튼이 한

### 운영자 콘솔 정보 배치(참가자 모바일 보류 중)

참가자 모바일 홈 구조는 고객사 결정을 기다리는 동안 **보류**하고, 운영사(대행사) 콘솔을 먼저 진행했다.
운영자 하루 흐름(준비 → 모집·안내 → 현장 → 마감) 기준의 독립 진단에서 나온 항목 중, 정책 결정 없이
고칠 수 있는 것을 반영했다.

- **경품 ↔ 추첨 연결 결함**: 경품이 가리키는 것은 추첨 프로그램(`source.programId`)인데 화면은 참여
  모듈 목록에서 이름을 찾고 있었다. 그 결과 업체 당첨 경품이 전부 `연결 추첨 확인 필요`로 떴다. 이제 추첨
  프로그램 이름을 정확히 보여주고, `추첨에서 수령자 지정` 링크는 해당 프로그램 행 앵커로 바로 이동한다.
- **참가자 그룹 지정 범위**: 그룹 지정은 지금 보이는 행에만 적용되는데, 같은 선택으로 메시지를 보내면
  숨김 포함 전체로 나간다. 조용한 부분 적용이던 것을 도구막대와 대화상자에 명시했다
  (`숨김 N명(그룹 지정 제외)`).
- **결과 보고서의 승인 대기 잔여**: 집계 카드에 `승인 대기 (명)`을 더하고, 보고서를 만들 때 남은 건수가
  있으면 “지금 집계로 고정되어 이후 승인은 반영되지 않는다”는 안내와 참가자 승인 처리 바로가기를 넣었다.
- **추첨 실행 전제**: 사유가 섹션 안내·행 힌트·비활성 상태로 흩어져 있어, 실행 행에 `실행 전제: …`
  한 줄로 모아 `aria-describedby`로 연결했다.
- **메시지 템플릿 채널**: 캠페인이 보낼 수 있는 MMS가 템플릿에는 없어 사진 공지 재사용이 불가능했다.
  서버가 허용하는 대로 MMS를 추가하고(이미지는 발송 시 첨부), 서버가 재시도를 거절하는 `FAILED` 캠페인에는
  다음 행동을 말해 주는 안내를 넣었다.
- **전광판 출력 선택**: 골라만 두고 적용하지 않은 상태를 표시해 “적용 전”을 알린다.
- **행사 종료 확인**: 종료하면 참가자 변경이 막히고 보고서가 생성 시점 값으로 고정되므로, 종료 확인란에
  그 사실을 넣었다.

검증은 새 소스 계약 `tests/console-operator-batch.test.cjs`와 격리 DB 콘솔 감사의 새 판정
`operator/information-batch`(보고서 승인 대기 → 참가자 그룹 지정 범위 → 추첨 전제 → 메시지 MMS →
전광판 미적용 → 종료 확인, 실제 화면 조작)·`rewards/draw-program-link`(추첨 실행으로 경품을 만든 뒤
프로그램 이름과 앵커 링크 확인)다. 참가자 모바일 홈 구조는 고객사 회신 전까지 손대지 않는다.
최신 빌드 `_nbCpr_JiLUnJC1DQ2O-q`에서 콘솔 감사 71판정·`npm test` 699·접근성 serious/critical 0을
통과했다. 원본 렌더는 `/tmp/opencode/eventouch-captures/console-unification/operator/`의
`rewards-draw-program.png`·`group-scope.png`·`report-approval-backlog.png`·`draw-prerequisites.png`·
`template-mms.png`·`display-unapplied.png`·`ended-report-reminder.png`에 있다.

**남은 운영자 후보(이번 회차 미반영)**: 데스크·부스 삭제 후 배정 행에 남는 고아 표시(데스크·부스 삭제
기능 자체가 없어 발생 조건이 낮음), `FAILED` 캠페인을 같은 내용으로 다시 만드는 흐름(서버가 재시도를
거절해 새 캠페인 생성으로 대체되며, 대상 재선택이 필요해 위험도가 있음), 경품 조회·수령 범위
(퇴장 데스크 한정 유지), 전광판 자동 갱신·보고서 자동 갱신(새 동작).

### 로그인 재설정 연락처

사용자가 “조직 관리자에게 재설정을 요청하세요”라는 안내에 실제 연락처가 없어 막다른 길이 된다고 지적했다.
로그인 화면에서 바로 연락할 수 있게 했다.

- 공개 `GET /api/auth/help`가 `ADMIN_EMAIL`·`ADMIN_NAME`(배포 환경에서 주입하는 조직 관리자)을 반환한다.
  **활성 AGENCY 계정이 있을 때만** 반환하며, 임의의 계정 목록·세션 정보는 노출하지 않는다.
- 로그인·스태프 로그인(공용 로그인으로 이동) 화면의 **`재설정 요청`**(밑줄 버튼)을 누르면 안내 패널이
  펼쳐지고 `관리자 연락처: <mailto:…>`가 나온다. 기본은 접힌 상태이며 Enter/Space·`aria-expanded`로
  동작한다. 관리자 설정이 없거나 조회에 실패하면 패널이 “등록된 관리자 연락처가 없습니다”로 설명하고
  로그인 자체를 막지 않는다.
- 주소는 배포 시 정하는 공개 연락처이며, 계정 이메일을 스크래핑해 보여주는 방식이 아니다. 320px에서도
  주소가 넘치지 않게 줄바꿈을 허용하고 링크 대비·포커스·44px 조작 높이를 유지한다.

서버 통합 테스트(`tests/server-auth.test.cjs`·`tests/server-setup-state.test.cjs`)로 관리자 있음/없음 응답과
세션 불필요를 확인했고, 실제 빌드의 로그인 화면에서 **접힘→펼침·키보드 토글·`mailto:`·미설정 폴백**을
320/390/1280px로 확인했다(연락처 응답은 라우트 모의, 엔드포인트는 실제 서버 테스트로 별도 검증).
증거: `/tmp/opencode/eventouch-captures/login-help/`의 `disclosure-contact-*.png`·`disclosure-no-contact-*.png`·
`disclosure-320-long-email.png`·`disclosure.json`. 검수 앱의 장기 실행 API는 이 변경 전 프로세스라 폴백
상태를 보여준다. 실제 배포는 `ADMIN_EMAIL`이 필수라 연락처가 표시된다.

### 전사 정보 필요성 검토(1차)

사용자가 “기획 적합성·정보 필요성·실제 업무 흐름 중심으로 전 화면을 다시 보고, 업무 단위로 진단→개선→조작
검증까지” 진행하기를 승인했다. 5개 업무 영역(참가자 접수·명단 / 안내·콘텐츠·편집기 / 참여 프로그램·추첨·경품·사진 /
현장 운영·보고서·설정 / 참가자·스태프·공개 화면)을 독립 진단하고, 진단 결과를 코드·서버 계약으로 재확인한 뒤
이번 회차에 아래를 반영했다. 진단에서 나온 정책 결정 항목은 아래 “남은 진단과 결정 대기”에 모았다.

- **참가자 명단**: 선택 계수 문구를 `현재 화면 N명 선택 · 전체 선택 M명`으로 바꿔, 필터 밖 선택 규모를
  명단 전체 인원으로 오해하지 않게 했다. 숨김 계수·200명 상한·초과 시 복구 행동은 그대로다.
- **명단 가져오기**: 유효 행이 승인 검토 없이 참가 확정으로 등록된다는 사실을 실행 버튼 옆에 명시했다.
  동의 기록 미생성 문구는 유지한다(서버는 가져오기에서 `consent=null`).
- **추첨**: 대상 문구를 서버 풀 조건과 맞춰 `입장(체크인)한 승인 참가자 전체 대상`으로 정정했다.
- **경품**: 상태 필터에 `연결 필요`(기프티콘 미연동)를 추가해 미연동 건을 바로 추릴 수 있게 했다.
- **참여 프로그램**: 추첨 카드에서 쿼터·등급·업체 추첨과 경품 연동은 추첨 화면에서 관리한다는 링크를
  추가했다(추첨 화면→프로그램 링크와 짝을 이룬다). 퀴즈 결과에는 채점이 앞뒤 공백을 제외한 완전 일치
  기준임을 명시했다.
- **참가자 홈**: 내부 영문 분류 배지(Utility/info/Engagement)를 참가자용 한국어(필수/안내/참여)로 바꿨다.
- **현장 운영**: 부스 잔여를 `인증 N회 · 잔여 M / 정원`으로 함께 보여주고, 부스 지도 초안이 게시본과 다르면
  참가자에게 무엇이 보이는지 안내한다. 데스크를 만든 뒤 고칠 수 없던 막힘은 기존 `desk.save` 수정 경로로
  해결했다(이름·작업·화면 편집, 방향 변경 시 서버가 요구하는 확인, 가동 상태 보존).
- **설정**: 참가비와 결제의 실제 관계를 참가비 입력 옆에 쓴다.

1차 진단 뒤 사용자 결정 세 건을 받아 추가로 반영했다.

- **참가자 부스 인증(셀프)**: 참가자 홈에 `부스 인증` 목적지를 추가하고, 스태프 스캐너와 같은 jsQR 카메라
  컴포넌트(공용 `app/CameraScan.tsx`로 이동)를 붙여 **앱 안에서 QR을 찍으면 바로 인증**되게 했다. 카메라가
  없거나 권한이 없으면 `ET:BOOTH:...` 코드를 붙여넣는 같은 제출 경로로 대체한다. 입장(체크인)·티켓 유효성·
  부스 상태·인원·횟수 한도는 모두 서버가 판정하고 화면은 결과만 보여준다. 스태프 SELF 안내도 실제 절차
  (QR을 보여주고 참가자가 직접 인증)로 바꿨다.
- **결제 기능 제거**: “행사 대행사 콘솔이 결제까지 관리하는 시스템은 아니다”라는 결정에 따라 설정의
  결제 기능 토글과 `유료·경품` 표기를 없애고, 참가비 옆에 “이 시스템은 결제를 처리하지 않습니다”를 명시했다.
  서버의 feature id와 모의 결제 명령은 API 호환을 위해 유지한다.
- **순위 투표 표기**: 추첨·투표 화면의 해당 섹션과 참가자 홈 타일을 `순위 투표`로 바꿔 참여 프로그램의
  `투표` 모듈과 구분했다.

검증은 새 소스 계약 `tests/console-information-review.test.cjs`, 격리 DB 콘솔 감사의 새 판정
(`ops/desk-edit`, `ops/map-draft-publish`, `draws/target-condition-copy`, `programs/draw-link`,
`settings/price-payment-hint`, `attendee/booth-scan-stamp`, `attendee/booth-self-stamp`,

Chromium에서 jsQR이 그 QR을 해독해 참가자 인증이 기록되는 것까지 확인했다(같은 참가자의 코드 재입력은
서버가 횟수 한도로 거부, 티켓 없는 탭은 안내 화면). 렌더·검증 원본은

**남은 진단과 결정 대기**(정책 변경·기능 확장이라 임의로 고치지 않았다. 사용자 결정이 필요하다):

- **참가자 홈 구조: 결정 완료(초기 심플 구성 유지)**. 고객사는 3개 후보 중 ① 기존 6타일 구성을 선택했고,
  근거는 "QR이 참가자들에게 제공되지 않을 수도 있다"였다. 위에 적은 대로 홈을 초기 구성으로 되돌렸고
  판정·계약도 그 결정에 맞춰 바꿨다. ②·③ 시안은 채택되지 않아 **제품에 반영하지 않았다**(비교 이미지·

- **인증 필수 행사의 사각**: 발송 자격증명이 없는 환경에서 연락처 인증을 켜면 신규 신청이 전면 차단되고
  현장 대체 접수 경로가 없다.
- **스태프 네임택 인쇄**: 입장 성공마다 인쇄 버튼이 노출된다(네임택을 쓰지 않는 행사에서는 소음).

### 필터 너비·높이·간격 재검토

테두리만 없애고 예전 폭 배분을 남겨 둔 문제가 있었다. 원본 렌더의 독립 디자인 검토(A)와 별도 브라우저

  드롭다운 폭으로 조정해 현재 Chromium에서는 약 81px가 됐다. 기본 선택 창·화살표·키보드는 그대로다.

### 행사 조회 필터 경량화

진행 단계 필터가 흰 카드처럼 보인다는 지적에 따라, 해당 기본 select의 흰 배경·둥근 테두리·그림자를

실기기·Safari·스크린리더 실청취는 여전히 미검증이다. 장기 실행 검수 세션이 만료되어 테스트 세션만 갱신했고
기존 행사·로그인 계정·데이터는 초기화하지 않았다.

### 모바일 상시 하단 메뉴 제거

사용자가 행사·고객사 두 목적지에 하단을 상시 할애할 필요를 지적했고, **하단 바 제거 + 상단의 작은
전체 메뉴**를 승인했다. 단순히 바만 숨기지 않고 다음 이동 경로를 구현했다.

- 모바일 상단 `메뉴`를 열면 기존 권한에서 허용된 `행사 목록`·`고객사`만 표시한다. 현재 행사 업무
  가로 탐색·별도 계정 메뉴·데스크톱 사이드바는 유지한다. 새 권한·설정 영역은 추가하지 않았다.
- 비모달 메뉴는 Enter/Space로 열고 첫 링크에 포커스를 둔다. Tab은 정상 순서로 빠져나가며,
  Escape는 실행 버튼으로 복귀한다. 바깥 입력을 클릭하면 메뉴만 닫고 입력 포커스는 빼앗지 않는다.
  전체 메뉴와 계정 메뉴를 동시에 열지 않고 데스크톱 폭으로 바꾸면 모바일 메뉴를 닫는다.
- 다른 목적지는 기존 미저장 경고를 통과해야 이동한다. 취소하면 입력·메뉴가 남고 승인하면 도착 후
  닫힌다. 현재 목적지를 다시 누르면 페이지를 초기화하지 않고 메뉴만 닫는다.
- 하단 바 전용 여백을 제거하고 일반 본문 끝 여백·safe-area만 남겼다. 상단 고정 메뉴에 대한 앵커
  여유는 유지한다. 좁은 화면에서 로고가 잘리던 것은 중복 메뉴 아이콘을 없애 해결했으며 글자 크기는 유지했다.

렌더와 전후 비교는 `/tmp/opencode/eventouch-captures/mobile-navigation/`의
`events-*.png`·`menu-open-*.png`·`event-menu-open-*.png`·`before-after-navigation.png`,
전체 메뉴의 닫힌 상태는 `mobile-cohesion/nav-final/`에 있다. 합성 검수 데이터의 구현 화면이며 모형이 아니다.
기존 검수 API/DB와 로그인은 유지한 채 해당 Next 프로세스만 최신 빌드로 바꿨다. 기존 배포·실제 사용자 데이터는 바꾸지 않았다.
최신 빌드의 **16메뉴 × 360/412/1280px = 48렌더**에서 가로 넘침·페이지 오류는 0이며,
320px에서도 메뉴와 24px 로고가 잘리지 않았다. 전체 테스트·콘솔·접근성·모바일·웹 감사는 직렬로 재통과했다.
로그는 같은 `mobile-navigation/`의 `build-final.log`·`tests-final.log`·`console-audit.log`·`a11y.log`·
`mobile.log`·`web-audit.log`다. 실기기·Safari·스크린리더 실청취·실발송은 미검증이다.
실제 조작 중 현재 목적지를 다시 눌렀을 때 메뉴가 닫히지 않던 이벤트 처리 오류를 발견해 수정했다.
설정 화면의 전용 미저장 경고에 공용 문구를 기대하던 감사 스크립트도 바로잡았으며, 취소 후 입력·메뉴 보존과
승인 후 실제 도착 검사는 그대로 유지한다.

### 모바일 스크린샷 지적 반영

사용자가 보낸 행사 목록의 좁은 검색칸·엇갈린 버튼·과한 상단 공간을 기준 사례로 삼았다.
이전의 넘침/접근성 통과는 배치와 업무 밀도의 수용 증거가 아니었음을 확인했다. 실제 기존 검수
픽스처를 유지한 채 콘솔 전체 메뉴의 모바일·데스크톱 렌더를 비교하고 다음을 반영했다.

- **행사 홈**: 검색을 첫 전체 폭 행으로, 단계와 승인 대기를 다음 행으로 분리했다. 카드/달력 전환은
  목록 제목 옆으로 옮기고 생성 버튼과 경쟁하지 않게 했다. 중복 수량 행·카드의 불필요한 여백을 줄였다.
- **공통 배치**: 첫 필터를 검색이라고 추측하던 CSS를 제거하고 전체 행/짧은 행동 쌍을 명시하게 했다.
  단일 헤더 보조 행동은 메뉴 제목 옆, 여러 행동은 메타 아래에 둔다. 섹션 제목과 보조 행동은 같은 행,
  긴 설명은 그 아래 전체 폭으로 읽는다. 실행 버튼·긴 한글의 줄바꿈·44px 목표는 보존했다.
- **참가자**: 검색은 항상 보이고 보조 필터는 모바일에서 펼친다. 접혀도 적용 개수·요약이 보이며,
  조건이 담긴 직접 링크는 펼쳐 시작한다. 검색/필터 초기화는 명단 선택을 버리지 않는다.
  CSV·가져오기는 짧은 보조 행동 쌍으로 유지한다.
- **설정·현장 운영·추첨·콘텐츠·편집기**: 화면 밖으로 잘리던 섹션 바로가기를 화면 안의 행으로 펼쳤다.
  실제 앵커 조작에서 제목이 상단 고정 메뉴 뒤로 가려지는 문제도 확인해 스크롤 여유를 적용했다.
  편집기 미리보기의 `실시간` 문구가 세로로 쪼개지지 않게 했다.
- **보고서**: 새로고침을 분석 제목과 정렬하고 조회 시각을 설명에 합쳐 지표 앞의 중복 행을 줄였다.
  동결 보고서·저장/게시/발송 명령·서버 권한·데이터 계약과 기존 사용자 작업은 바꾸지 않았다.

최신 전후 이미지·뷰포트 측정은 `/tmp/opencode/eventouch-captures/mobile-cohesion/`의
`before/`·`after/`·`before-after-{events,participants}.png`에 있다. 구현된 화면의 비교이며 모형이 아니다.
당시 빌드 `fSurxUw_079JkzeSTmmIK`의 **16메뉴 × 360/412/1280px = 48렌더**에서 가로 넘침·페이지 오류는
0이었다. 같은 픽스처·360/412px에서 첫 행사 카드는 **y467→410px**, 첫 참가자 행은 **y644→560px**로
앞당겨졌으며, 글자·44px 조작 영역을 줄인 결과가 아니다. 공개 홈·신청·로그인·배정 스태프 화면도 실제 경로로 확인했다.
Native Review는 DOM에 접근하지만 여전히 visible-tab 캡처 오류가 있어, 렌더 근거는 저장소
Playwright/Chromium 원본 이미지다. 실기기 소프트 키보드·Safari·스크린리더 실청취·직원 수용은 미검증이다.
검증 도구의 실패도 구분했다. 기존 감사 DB의 기본 관리자 계정과 통합 테스트의 시드가 달라 발생한 로그인 실패는
기존 DB를 지우지 않고 별도 회귀 DB로 분리했다. 두 탭 검사는 서버가 정상적으로 자르는 끝 공백까지 그대로
저장되길 기대하던 픽스처를 정규 값으로 고쳤다. 필드 보존·실제 DB 재조회 조건은 그대로 유지한다.

### 메뉴별 구조 중앙화

사용자가 이후 “화면별로 다 제각각”이라고 지적하고 전체 개선을 승인했다. 아래의 이전 국소 검수에서
“관찰 범위의 중대한 회귀 없음”이라는 평가는 **메뉴 간 일관성의 수용을 뜻하지 않는다**. 이를 별도 목표로 삼아
전체 콘솔 메뉴의 공통 프레임을 실제 코드에 적용했다.

- `console-navigation.ts`가 기존 메뉴 이름·경로의 정본이다. `ConsoleShell`과 `ConsolePage`가 이를 공유한다.
  큰 제목은 메뉴명, 행사명은 작은 문맥 링크로 통일하고, 공통 폭·시작선·도구막대·섹션·편집 폭·작업 행·
  피드백·대화상자를 중앙화했다. 달력·지도·추첨 결과·사진·실제 참가자 홈 미리보기는 고유 내용을 보존한다.
- 참가자 도구막대의 등록/내보내기·조건별 목록·선택 작업을 구분했다. 미입장 링크는 실제 미입장 조건과
  눈에 보이는 필터를 함께 적용한다. CSV는 현재 보이는 범위와 수를 알리고 수식으로 실행될 텍스트를 방어한다.
- 각 업무의 실제 입력 차이와 미확인 요청만 공용 이탈 경고에 등록한다. 미입력 창·조회 필터·저장 완료 상태는
  경고하지 않는다. Escape/배경/취소는 한 폐기 확인만 거치며, 쓰기 중에는 동기 ref로 닫힘을 막는다.
  서버 결과 불명과 입력 폐기는 구분한다. 브라우저 뒤로/앞으로·탭 종료 후 입력 복원이나 오프라인 저장은 보장하지 않는다.
- 참가자 페이지의 응답 유실 뒤 새 입력에 이전 영수증이 재사용되어 입력을 덮을 위험을 수정했다.
  요청은 불변 입력 지문에 묶고 새 입력은 보존하며, 서버 버전 충돌은 확인·내 변경 적용·재저장으로 복구한다.
- 설정·경품·현장 운영의 표시 권한은 실제 로그인 계정과 행사 배정으로 판단한다. 보관 행사의 쓰기와 종료된 행사의
  참가자 변경을 서버와 맞춰 막고 이유를 알린다. 읽기·내보내기·미리보기는 유지하며 새 권한 정책을 만들지 않았다.
- 보고서 인쇄는 선택한 저장 보고서만 복제해 출력한다. 변하는 실시간 분석과 다른 보고서가 동결 보고서에 섞이지 않는다.

공통 구성 규칙은 `docs/DESIGN-SYSTEM.md`, 현재 검증 결과는 위 검증 수치에 기록한다. 아래는 이 중앙화에 앞선
업무별 개선과 그 당시의 증거다.

### 사용 사례 UX 보강(독립 검토 3건 반영)

구현 완료 후 “사용성이 중요하다”는 요청에 따라 화면별 기능 구성이 아니라 실제 사용 사례를 기준으로
독립 UX 검토 3건을 수행했다. 검토 결과 중 사용자의 업무가 막히거나 오해를 만드는 항목을 반영했다.

- **참가자**: 경품 기능이 켜져도 확정자에게 상태 변경(취소·대기)이 사라지던 문제 수정. 행 빠른 행동과
  상태 변경을 함께 제공하며 종료·보관 제한은 유지한다.
- **명단 가져오기**: 60/120/200자 초과를 조용히 자르던 것을 행 번호가 있는 필드 오류로 바꾸고,
  검토 단계에 실제 반영 값 표본과 `유효 N행 반영` 수를 표시한다.
- **메시지**: 동명이인 구분을 위해 참가자와 같은 마스킹 연락처를 표시하고, ‘선택 대상만 보기’가
  상태·검색 조건 때문에 선택자를 숨기던 것을 선택 전체 검토로 바꿨다.
- **현장 운영**: 부스를 만든 뒤 열 수 없던 막힘을 기존 `booth.save` 편집으로 해결하고, 데스크가 없어도
  부스 업무 배정이 가능하게 했다(진행 중 전환의 데스크 요건은 유지).
- **행사·고객사·팀**: 승인 대기 필터 초기화 버그, 행사 카드의 대기 처리 직접 이동과 조회 상태 URL 보존,
  연락처 없는 고객사의 사업자등록증 접근·목록 검색, 1회 초대 링크가 긴 목록 뒤에서 소실되던 배치 수정과
  닫기 전 경고, 미지정/담당 행사·만료 표시.
- **경품·편집기·수리**: 업체 당첨 `PENDING`을 오류가 아닌 ‘수령자 지정 대기’로 표시하고 추첨 지정으로
  연결. 편집기 충돌 복구는 내가 실제 바꾼 항목만 최신 초안에 적용하여 다른 운영자의 설정을 덮지 않는다.
  추첨은 운영 목록을 생성 폼보다 앞에 두고 실행 전제조건을 행동 옆에 표시, 빈 룰렛 행의 가짜 미저장 판정을
  제거했다. 보고서는 동결 스냅샷의 그룹 인원·승인 사진·집계 기준 시각을 출력하고 현재 분석의 조회 시각과
  새로고침을 구분한다.
- **프로그램**: 기능이 꺼진 유형의 쓰기를 서버 거절 전에 차단하고 설정 링크를 제공한다.

반영 후 전체 테스트가 통과했고(수치는 위 검증 수치가 정본), 검토에서 나왔던 잔여 항목은 다음 절에서 다룬다.

이번 렌더는 저장소 Playwright/Chromium으로 캡처하고 원본 이미지와 실제 조작 결과를 직접 검토했다. Native Review는
로그인·DOM·입력·현재 메뉴 제목을 확인했지만 캡처 엔진의 visible-tab 오류가 있어 렌더 검증 근거로 쓰지 않았다.
같은 빌드의 별도 Chromium 조작에서 표준 `beforeunload` 경고도 확인했다: 새로고침 취소 시 입력 유지,
승인 시 저장본으로 복귀, 변경된 탭 닫기 승인 시 종료. 증거는 같은 폴더의 `guard-native.json`이다.
`before-after.png`는 참가자·메시지·설정의 실제 구현 전후 구조 비교이며 모형이 아니다(합성 데이터는 서로 다름).
기존 API/데이터/아카이브·사용자 파일과 디자인 정체성은 보존했다. 실기기·Safari·스크린리더 실청취·실프린터·Excel
직접 열람·직원 실사용/최종 인수는 미검증이다. 이번 공통 구조의 로컬 구현·통합 검증이 전체 납품 마감을 뜻하지는 않는다.

### 이전 업무별 개선

사용자의 직원 사용성·흐름·불필요한 설명 검수 요청에 따라 구조·문구·실제 렌더를 독립 검토했다.
UI Pilot 스킬/도구는 이 환경에서 사용할 수 없어 사용했다고 부르지 않는다. 소스 검토 둘과
독립 렌더 검토를 종합하고, 설계 담당자가 원본 화면과 실제 상호작용으로 판단했다.
직원 대상 실사용 실험이나 전체 제품 수용 완료를 뜻하지 않는다.

| 업무 문제 | 반영 |
|---|---|
| 긴 참가자 카드와 흐트러진 상태 열 | 데스크톱 행 밀도·고정 열 정렬, 모바일 읽기/조작 영역 보존. 필터를 주소에 반영하고 숨겨진 선택 수를 알린다. |

| 현장 버튼 비활성 이유·기술 오류 노출 | 데스크/부스 선택 안내·입장/퇴장 버튼 구분, QR 원시 코드는 펼침/복사 피드백 분리. 공개 오류는 기술 메시지 대신 복구 안내·정상 main 랜드마크, 주버튼 hover는 기존 고대비 토큰 사용. |

## 실행

```bash
npm run setup                 # 루트 + apps/web 의존성 설치
npm run build                 # API 타입 검사 + Next 제품 빌드
npm start                     # DATABASE_URL 등 실행 환경 필요, API 8776 + Next 8777 감독 실행
npm run dev                   # API + Next 개발 서버 감독 실행
bash scripts/serve-demo.sh     # 기존 데모 DB/스토리지를 유지하는 제품 감독 실행
```

백엔드 단독 작업은 명시적으로 실행한다. 브라우저 제품 진입점은 항상 Next다:

```bash
npm run api:start              # API만 실행, 제품 HTML/정적 저장소 파일은 제공하지 않음
```

검증용 DB를 붙여 돌릴 때:

```bash

EVENTOUCH_A11Y_DATABASE_URL='postgres://eventouch@localhost/eventouch_uiux_audit?host=/tmp/opencode/eventouch-pg-test-auth.l0FjK5' npm run a11y
```

브라우저 감사는 Playwright Chromium 설치(또는 `CHROMIUM_EXECUTABLE` 명시)와 최신 `npm run build`가
필요하다. `a11y`·`mobile`·`web:audit`는 기존 `.next`로 임시 Next를 직접 실행하며 SSR도 같은
격리 API를 보게 한다. 이 세 명령은 `WEB_BASE`를 대체한다고 알리고 외부 서버를 검수했다고 주장하지
않는다. 정상 경로의 준비 표식·역할·주소를 검사하므로 오류/404/로그인 화면으로 통과할 수 없다.
가져오기·한울·테마·은퇴 감사는 여전히 실행 중인 `WEB_BASE`(기본 `http://127.0.0.1:8777`)가 필요하다.
모두 실제 API를 격리 DB 스키마로 실행하고 종료 시 자기 fixture만 정리한다. 전체 테스트와 DB
브라우저 감사는 직렬 실행한다.

운영 배포 위치(NAS·공개 도메인)와 값은 아직 정해지지 않았다 — `docs/DEPLOY.md`.

## 결정 (유효)

- 문자·알림톡은 Solapi 직결. 자격증명·발신번호·승인 템플릿이 준비되면 실발송을 후검증한다.
- 요금은 행사대행 운영사 부담. 결제·환불·기프티콘은 v1 제외(모의 발송만).
- 오프라인 로그인·셸 캐싱·스캔 큐를 제공하지 않는다. 연결 오류를 안내하고 온라인에서 재시도한다.
- 구 앱은 완전 은퇴했다. API/DB 폴백 이름에 `legacy`가 있어도 사용자 데이터 보존 경로와
  사업 계약은 구 프론트엔드와 구분해 유지한다. 과거 구 화면 수/로드 순서는 현재 개발 기준이 아니다.
- 내비게이션 정본: 메인 메뉴는 `행사`·`고객사` 두 개, 현재 행사는 `행사` 아래 중첩,
  `팀·권한`·`서비스 연동`은 하단 운영자 메뉴. 새 "조직 설정" 영역은 만들지 않는다.
- 진입 정본: 공용 로그인은 `/login`이며 `?next=`는 로컬 allowlist만 허용하고 도착 화면이
  역할·배정을 서버 기준으로 재확인한다. `/staff/login`은 호환 리다이렉트로 유지한다.
  `/staff`는 배정 입구, 실제 현장 업무는 `/staff/events/:id`에 둔다(입구는 스태프별, 업무는 행사별).
- 고객사는 운영사의 내부 기록이다. 고객사 포털·로그인은 제공하지 않는다.
  고객사 담당자(CLIENT 역할) 미지원은 출시 블로커가 아니라 의도적 제외다.

### 적대적 재검증 루프(2차)

앞선 검증이 기본 상태 중심이었다는 지적에 따라, 새 기능을 깨보는 적대적 검토와 경계 조작을 한 바퀴 더 돌렸다.
확인된 결함을 고치고 다시 검증하는 루프를 거쳤다.

- **퀴즈 결과**: 퀴즈를 투표처럼 선택지 집계하던 오류를 수정. 무료 텍스트 응답을 묶어 분포를 보이고
  저장된 정답과 비교해 `정답/오답/미채점`을 표시한다.
- **MANAGER 팀 활동**: 보안 패널 403에서 로더가 조기 반환해 활동이 영구 로딩되던 문제를 수정.
  활동은 별도로 로드하고 명시적 빈/오류 상태를 쓴다(실제 MANAGER 세션으로 확인).
- **200명 초과 인계**: 숨김 선택 때문에 막힌 채 안내만 있던 것을 선택/숨김/한도 수치와
  `숨김 제외` 복구 행동으로 풀었다(201명 실제 선택으로 확인).
- **13번째 프로그램 생성**: 생성 결과가 더 보기 뒤로 숨던 것을 새 카드 공개·스크롤·포커스로 연결했다.
- **키보드 더 보기**: 펼친 행이 포커스를 건너뛰던 문제를 첫 새 행 포커스로 수정(팀·메시지·프로그램·사진 공통).
- **셸 자체 오류**: bootstrap 실패를 숨기고 빈 내비게이션을 보여주던 것을 경고 배너+다시 시도로 바꿨다.

이후 모바일 스크린샷 반영 검수에서 두 탭의 충돌/필드 병합과 사진·메시지·프로그램의 중간/최종 펼침은
영구 브라우저 감사로 검증했다. 경품 초기 빈 목록도 최신 렌더에서 확인했다. 여전히 미검증인 추가 경계는
극단적인 한글/장문·큰 글자 전체 조합, 기능을 끈 모든 모듈의 직접 URL, 경품 수령 필터의 모든 데이터 상태다.
이 항목들은 결함으로 단정하거나 검증 완료로 세지 않는다.

독립 UX 검토 3건에서 남았던 항목을 순차 반영했다. 각 항목은 격리 API/DB의 실제 브라우저 조작
(`ux-flows.json`)과 소스 계약 테스트로 확인했다.

1. **명단→메시지 인계**: 참가자 화면에서 선택한 명단(숨김 선택 포함, 200명 상한)을 `?to=`로
   메시지에 넘기고, 유효·제외 수를 안내한 뒤 선택 대상만 보기로 검토한다. 자동 발송·새 API 없음.
2. **참여 프로그램 결과**: 카드의 `결과 보기`에서 투표·퀴즈 항목 집계, 만족도 문항별 응답/평균,
   Q&A 답변/미답변, 사진 승인/대기를 이미 불러온 데이터로 계산한다. 참가자별 식별 정보는 노출하지 않는다.
3. **게시본 비교**: 편집기 미리보기에 `편집 중 / 게시본` 전환을 추가했다. 게시본은 실제 참가자 홈
   컴포넌트로 읽기 전용 표시하며 편집값을 건드리지 않는다.
4. **팀 최근 활동**: 원시 커맨드 키를 한국어 행동명으로 바꾸고 8건 + `더 보기`로 줄였다.
5. **경품 도구**: 이름·소속·경품명·추첨명 검색과 상태 필터, 결과 수, 초기화, 조건 불일치 빈 상태를 추가했다.
6. **긴 목록**: 참여 프로그램·현장 사진·발송 기록·팀 활동은 처음 12/12/10/8건 + 증분 `더 보기`로
   보여준다. 가상화 라이브러리는 쓰지 않았고, 수천 건 규모의 성능은 여전히 미검증이다.
7. **공지 📌**: ‘고정됨’ 배지와 중복이던 이모지 마커를 제거했다.

이로써 이 검토 목록은 비워졌다. 남은 것은 아래 블로커·미검증(실발송·실기기·정책 확정·배포)이다.

한울 기획안의 **앱 구현과 로컬 통합 검증은 완료했지만 실제 행사 운영 준비 전체는 완료가 아니다**.
기존 이력의 `끝까지 구현`·`레퍼런스에 맞췄다`는 서술은 완료 판정으로 쓰지 않는다.
이전 홈은 슬라이드 설명 막대·번호 주석을 UI로 잘못 옮겼고 고객이 거절했다.
현재 홈은 PDF 3·4쪽 왼쪽 휴대폰 이미지의 원본 배너 아트·흰색 2열 타일·분리 상세를 따른다.
설정 가능한 정확한 투표 선택 수·개시/마감,
독립 룰렛 운영 시간·재고, 업체/그룹별 추첨 자격·등급·중복 범위, 사전 럭키번호 배정,
STAFF 대상자별 경품 조회·수령, 공개 결과 게시/개인정보 경계의 **서버 기능과 DB 행동 검사**는
구현했고 운영 콘솔·참가자·STAFF·무대 화면의 실제 API/DB 연결 흐름도 통과했다.
모바일 룰렛의 경품 섹터·실제 당첨 칸 정지·재접속 복원도 최종 빌드에서 검증했다.
엑셀 라이브러리의 알려진 취약점 교정과 XLSX/XLS 표시 연락처·응답 유실 재시도 감사도 통과했다.
기존 브라우저 모의 응답 증거는 실제 API·DB 통합 증거가 아니다.
